# Precomputed FFT2D5 path geometry and projection reuse

Implemented locally in the existing `FFT2D5Algorithm.h/.hpp/.cpp`, without new solver classes or source files. One preparation call is made at the start of each complete solve. It builds the current solve-frame segment geometry and computes each active particle's local coordinates and nearest segment. Coverage checking, deposition and gather reuse those coordinates. Standalone diagnostic stages retain fresh uncached conversion.

## Runtime and results

Same 100-step pilot: 100,000 matched KV particles, full DBA ring, 5.602212 nC, 64×64×512, transverse widths 64 mm, 3 ps, four OpenMP threads, one MPI rank, ORIGINAL transverse space charge and longitudinal force disabled. The input and native initial checkpoint are byte-identical across runs.

| Executable/run | Wall time | Speedup against fresh baseline |
|---|---:|---:|
| Original, fresh baseline | 73.652 s | 1.000× |
| Optimized, run 1 | 54.850 s | 1.343× |
| Optimized, run 2 | 50.779 s | 1.450× |
| Optimized, separate kernel profile | 52.425 s | 1.405× |

The uninstrumented runs reduce wall time by **25.5–31.1%**; their average is 52.815 s, approximately 28.3% less than baseline. These are bounded short-run measurements, not a guaranteed long-run rate.

All 100,000 IDs and the charge are retained; all arrays are finite at t=300 ps/global step 99. Across both optimized runs and the separate profile, maximum differences from the fresh baseline are below **4.9e-13 m** in laboratory position and **1.81e-12** in beta-gamma momentum. The momentum difference is at most **0.00335% of the reference space-charge impulse scale**. All ten saved RMS/emittance samples agree to relative differences below **1.75e-14**.

These comparisons concern numerical preservation by the optimization; they do not establish long-term accuracy or agreement of the original slice approximation with a curved Coulomb reference. No 16-turn run was started. The measured rate still extrapolates to weeks for sixteen turns at 3 ps.

## Where the saving comes from

The same read-only Kokkos timer plugin used in the preceding profile reports:

| Kernel work, per 100 steps | Before | After |
|---|---:|---:|
| Path geometry preparation | — | 0.00127 s |
| Particle projection preparation | — | 11.2984 s |
| Deposition, including coordinate conversion | 16.5930 s | 0.1141 s |
| Gather, including coordinate conversion | 16.4825 s | 0.0724 s |
| **Combined** | **33.0755 s** | **11.4862 s** |

Geometry preparation and particle projection each execute exactly 100 times for the one active container: once per field solve. The combined cost falls by about 65%. The slice solver remains unchanged, with 512 occupied slices per solve. The plugin reports zero callback errors and no pending spans.

## Implementation and memory

`preparePathGeometryAndProjections(context)` uses two ordered device stages: one small sequential geometry kernel, then a parallel projection kernel per active container. It stores six doubles per segment: direction, squared length, length and cumulative length. The squared length retains the original division in the nearest-point calculation. Search order, clamping, zero-length segment handling and first-nearest tie selection are unchanged. Pre-summing arc length changes floating-point association slightly; the comparisons above quantify the resulting differences.

For 2,606 segments and 100,000 particles, the additional payload is **125,088 bytes** for geometry plus **3,200,000 bytes** for local coordinates and segment indices, about **3.17 MiB** combined. Workers share the tables. Buffers are reused but entries are refreshed for every complete solve; count changes resize the per-container buffers. Inactive containers retain their state. No particle-by-segment distance matrix is allocated. The remaining search still has O(N*M) work, performed once per solve.

The existing conversion function reads cached positions/bases during the complete pipeline and computes momentum components from current particle momenta for diagnostics. Explicit per-call stage arguments prevent a stale global cache-active flag after exceptions. Diagnostic stages called separately use uncached conversion.

## Validation and documentation

The existing configuration, algorithm and numerics CTest targets pass with one and four OpenMP threads. The existing two-rank test confirms unsupported distributed execution is still rejected. A new test in the existing algorithm test file compares deposited density and every E/B component against the original uncached stages, with nonuniform segments, a repeated vertex, a corner tie, periodic-seam probes, invalid particles, particle-count changes, reordering and momentum changes. Independent mirrors prevent CPU aliasing from making this comparison tautological. Existing frame-invariance and exception-restoration checks also pass. No physics tolerance was changed.

Detailed Doxygen documents the preparation function's formulas, frame requirements, storage, complexity, cache lifetime and rounding behavior. Doxygen parsed the private function and generated its XML description without warnings. GPU execution was not checked in this laptop study.
