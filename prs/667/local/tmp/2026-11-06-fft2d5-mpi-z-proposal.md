# FFT2D5 MPI decomposition along the path coordinate

Proposal only, 6 November 2026. No MPI solver implementation or multi-rank run has been made. Keep the preserved one-rank reference and physics model unchanged. No IPPL source changes.

Use the 3D OPEN particle-mesh infrastructure as the starting point: ippl::FieldLayout z-only slabs, ParticleContainer.updateLayout/update for migration, rho.accumulateHalo after deposition and electric.fillHalo before gathering. The important difference is that FFT2D5 ownership is based on its logical longitudinal path length s (called z in the auxiliary mesh), not laboratory Cartesian Z. Every rank owns full transverse planes. No 3D FFT is introduced.

Initial implementation sequence:
1. Permit PARFFTX=FALSE,PARFFTY=FALSE,PARFFTZ=TRUE for FFT2D5 MPI. Static equal z slabs first; retain serial default/reference path.
2. Reuse the cached path projection for ownership. Temporarily expose (u,v,s) as migration positions and preserve exact Cartesian positions in a registered particle attribute with suitable container lifetime. Existing migration must carry all registered fields (IDs,P,Q/dt,etc) together. Restore Cartesian positions before tracking; never reconstruct them approximately from a clamped path projection. Audit all other calls to migration/layout-dependent operations so no logical layout sees Cartesian coordinates. Start with rebuilding projection caches after migration, since particle order and local counts change; optimize by migrating projection attributes only after correctness.
3. Retain current FFT2D5 CIC/normalization and field reconstruction. Its custom deposition already uses the layout's global-to-local index offset. Add IPPL charge halo accumulation, adapting periodic/open physical boundaries so internal rank interfaces do not become beam ends or locally wrap. x/y boundaries remain open. Gather uses IPPL field halo fill plus existing interpolation/reconstruction.
4. Each rank solves only its owned slices with existing batch64 kernels. A complete transverse FFT plane stays on one rank/GPU. Use the existing direct heFFTe backend with MPI_COMM_SELF. IPPL's high-level RC FFT currently constructs plans on global ippl::Comm even for a self field layout; therefore local batch plan and Green-spectrum initialization must bypass that wrapper in OPALX. Do not temporarily replace the global communicator or patch IPPL.
5. Compute line density over owned complete transverse planes, then MPI_Allgatherv just the Nz line-density values. At Nz512 this is4KiB/rank. Keep the existing global gradient/interpolation formulas and global end conditions. This avoids introducing separate distributed gradient halos at this stage. Beam moments, reference frames, charge normalization and timestep remain globally consistent; never substitute rank-local beam means.

For Nz512 and batch64: 1rank512slices8batches;2ranks256slices4batches;4ranks128slices2batches. Memory for3D charge/field grids should approximately scale1/P, with full transverse FFT workspace retained perrank. Particle migration, field halos, global moments and a small line-density collective remain. FFT transposes stay local to each rank; distributed3DFFT communications from OPEN are not needed.

Reuse actual particle migration rather than add manual contribution routing and a home-rank return protocol. Existing OPEN already supports ownership changes. This avoids the proposed replicated-global-grid scaffold as the main implementation. The coordinate staging and cached-view invalidation need careful exception-safe handling. Persistent scratch attributes must outlive their registration; no temporary unregistered view can be assumed to migrate.

Validation: frozen identical-source fields at1/2/4ranks, allthreecomponents; rank-boundary/CIC and closed-ring seam cases; open ends, empty ranks/slices, neutral sources and nonuniform longitudinal density. Assert totalcharge/IDs and compare physical output indexed byID, not local order. Then100stepDBA and charged bend with OPEN longitudinal model against the preserved1rankreference, including rms/emittances, runtime, memory and migration/halo cost. Only then repeat one fullturn. No new physical model, ORB balancing or16turn runs initially. Equal slabs suit the uniform coasting DBA; a localized bunch may leave slabs empty, so load balancing is a separate follow-up using existing one-axis machinery where suitable.
